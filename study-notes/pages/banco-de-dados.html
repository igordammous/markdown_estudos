1. O que são Banco de Dados

Um banco de dados (BD) é uma coleção organizada e estruturada de dados persistentes, relacionados entre si, que representa aspectos do mundo real (o chamado mini-mundo ou universo de discurso). Ele é projetado, construído e povoado com dados para atender a um propósito específico (Elmasri & Navathe).

Além dos dados em si, um banco de dados inclui:

  • Metadados: informações sobre a estrutura dos dados (dicionário de dados ou catálogo).
  • Restrições de integridade: regras que garantem a validade e consistência dos dados.
  • Operações: formas de consultar e modificar os dados (geralmente via SGBD).

1.1 Analogia: Biblioteca organizada

Imagine uma biblioteca antiga, onde os livros eram armazenados sem nenhum critério. Encontrar um livro era uma tarefa de horas, e perder um exemplar era comum.

Agora imagine uma biblioteca moderna:

  • Cada livro tem uma catalogação (título, autor, assunto, ISBN).
  • Há prateleiras organizadas por categorias e ordem alfabética.
  • Existe um catálogo (fichário ou sistema digital) que referencia cada livro.
  • Há regras de empréstimo, devolução e reserva.

O banco de dados é exatamente essa biblioteca: dados organizados, com catálogo (metadados), regras (integridade) e operações definidas (consultar, inserir, remover).

1.2 ALCOA++

Embora a ALCOA++ não seja um tópico central nas bibliografias clássicas de banco de dados (Elmasri, Silberschatz, Date), ela é fundamental na gestão de dados regulados, especialmente nas indústrias farmacêutica, química e alimentícia, dentro do contexto de qualidade, integridade e governança de dados. ALCOA++ é um conjunto de princípios que garante a integridade dos dados em ambientes regulados. Ele surgiu a partir de diretrizes de boas práticas de fabricação (GMP), boas práticas de laboratório (GLP) e boas práticas clínicas (GCP), sendo amplamente adotado por agências reguladoras como FDA (EUA), EMA (Europa) e ANVISA (Brasil).

O objetivo é assegurar que os dados sejam confiáveis, rastreáveis e defensáveis ao longo de todo o ciclo de vida — desde a geração até o arquivamento.

1.2.1 Por que isso importa para bancos de dados?

Quando falamos de banco de dados, normalmente pensamos em eficiência, consistência e segurança. A ALCOA++ acrescenta uma camada de conformidade regulatória, exigindo que os sistemas de banco de dados em indústrias reguladas sejam capazes de auditar cada alteração, rastrear cada acesso e preservar cada registro.

1.2.2 Atributos

1.2.2.1 Atribuível (Attributable) [A]

Cada dado deve estar associado à pessoa ou sistema que o gerou, modificou ou excluiu. Exemplo em banco de dados:

  • Registro de created_by, updated_by, deleted_by em tabelas de auditoria.
  • Login único por usuário (sem contas compartilhadas).
1.2.2.2 Legível (Legible) [L]

Os dados devem ser legíveis e permanentes, sem possibilidade de rasuras ou alterações que comprometam a leitura. Exemplo:

  • Uso de INSERT e UPDATE com auditoria imutável (tabela de histórico).
  • Não usar DELETE em dados críticos; usar flag de "inativado" ou soft delete.
1.2.2.3 Contemporâneo (Contemporaneous) [C]

Os dados devem ser registrados no momento em que a atividade ocorre, não depois. Exemplo:

  • Captura automática de data e hora (timestamp) no momento da gravação.
  • Triggers ou eventos de banco que gravam automaticamente o horário real do evento.
1.2.2.4 Original (Original) [O]

O dado deve ser a primeira versão registrada, não uma cópia ou recriação. Exemplo:

  • Armazenar o dado bruto original antes de qualquer transformação.
  • Versionamento de registros (ex.: tabelas historico_* ou colunas versao).
1.2.2.5 Preciso (Accurate) [A]

Os dados devem estar corretos e refletir fielmente a realidade. Exemplo:

  • Validação de dados na entrada (constraints, triggers).
  • Uso de tipos de dados adequados (não armazenar data como string, por exemplo).
1.2.2.6 Completo (Complete) [++]

Todos os dados relevantes devem ser registrados, incluindo falhas, erros e correções. Exemplo:

  • Auditoria de tentativas de login, alterações de configuração, exclusões lógicas.
  • Logs completos de transações, mesmo as que falharam.
1.2.2.7 Consistente (Consistent) [++]

Os dados devem seguir uma ordem lógica e coerente ao longo do tempo. Exemplo:

  • Sequência de timestamps coerente (sem datas no futuro, sem horários impossíveis).
  • Regras de normalização e integridade referencial para evitar contradições.
1.2.2.8 Duradouro (Enduring) [++]

Os dados devem ser armazenados em mídia durável e legível por todo o período de retenção exigido. Exemplo:

  • Políticas de backup e retenção.
  • Migração de mídia legada sem perda de legibilidade.
1.2.2.9 Disponível (Available) [++]

Os dados devem estar disponíveis para revisão, auditoria ou inspeção quando necessário. Exemplo:

  • Índices e estruturas que permitam consulta rápida de históricos.
  • Replicação e alta disponibilidade do banco de dados.

1.4 Importância dos Bancos de Dados

Os bancos de dados são a espinha dorsal de praticamente todas as aplicações modernas. Sem eles, a gestão da informação seria caótica, redundante e insegura.

1.4.1 Vantagens principais (segundo Elmasri & Navathe e Silberschatz)

  • Controle de redundância: cada dado é armazenado uma única vez, evitando inconsistências.
  • Compartilhamento de dados: múltiplos usuários e aplicações acessam os mesmos dados simultaneamente.
  • Restrições de integridade: regras garantem que os dados sejam válidos e coerentes.
  • Segurança: controle de acesso, autorização e auditoria.
  • Independência de dados: mudanças na estrutura física não afetam as aplicações.
  • Acesso eficiente: consultas otimizadas por meio de índices e heurísticas.
  • Recuperação de falhas: transações e backups protegem contra perda de dados.
  • Concorrência: múltiplos usuários acessam sem conflitos (controle de transações).

1.4.2 Analogia: Conta bancária

Imagine um banco sem banco de dados:

  • Cada agência teria seu próprio cadastro de clientes.
  • Um cliente poderia sacar mais do que tem em outra agência.
  • As transações não seriam registradas de forma segura.
  • Não haveria como garantir que o saldo está correto.

Com um banco de dados:

  • O saldo é único e consistente.
  • As transações são registradas e protegidas (ACID).
  • Há controle de acesso para funcionários e clientes.
  • Há recuperação de falhas em caso de queda de energia.

1.5 Evolução

1.6 SGBD (Sistema Gerenciador de Banco de Dados)

O SGBD é o software que gerencia o banco de dados. Ele atua como intermediário entre os usuários e os dados, garantindo consistência, segurança e eficiência.

1.6.1 Funções principais

  • Definição de estrutura (DDL – Data Definition Language).
  • Manipulação de dados (DML – Data Manipulation Language).
  • Controle de acesso e concorrência.
  • Otimização de consultas.
  • Recuperação de falhas.

1.6.2 Analogia: Maquinário do banco

Se o banco de dados é o cofre com dinheiro, o SGBD é o caixa eletrônico:

  • Ele autentica o usuário.
  • Valida a operação.
  • Atualiza o saldo.
  • Registra a transação.
  • Recupera o sistema em caso de falha.

2. Modelos de Banco de Dados

Um modelo de banco de dados é um conjunto de conceitos e regras usados para descrever a estrutura, as operações e as restrições de um banco de dados. Ele define como os dados são organizados, armazenados e manipulados.

  • Modelo hierárquico (década de 1960)
  • Modelo em rede (CODASYL)
  • Modelo relacional (1970 – E. F. Codd)
  • Modelo orientado a objetos
  • Modelo NoSQL (documento, chave-valor, colunar, grafo)

2.1 Modelo Relacional

O modelo relacional organiza os dados em tabelas (relações), onde cada linha representa uma entidade ou fato, e cada coluna representa um atributo. As relações entre tabelas são feitas por meio de chaves primárias e chaves estrangeiras.

2.1.1 Exemplo: Planilhas interligadas

Imagine uma planilha de Excel para "Clientes" e outra para "Pedidos". Na planilha de Pedidos, há uma coluna "ID_Cliente" que referencia a linha correspondente na planilha de Clientes. Essa é a ideia de chave estrangeira.

Exemplo prático

Tabela clientes

id_clientenomeemail
1Ana Souzaana@email.com
2Bruno Limabruno@email.com

Tabela pedidos

A relação entre pedidos.id_cliente e clientes.id_cliente garante que todo pedido pertence a um cliente válido.

2.1.2 Características técnicas

  • Álgebra relacional: operações como seleção (σ), projeção (π), junção (⋈).
  • Restrições de integridade: entidade, referencial e de domínio.
  • Normalização: evita redundância e anomalias de atualização (1FN, 2FN, 3FN, FNBC).
  • ACID: Atomicidade, Consistência, Isolamento, Durabilidade.

Imagine uma tabela de resultados de testes laboratoriais em um banco PostgreSQL:

CREATE TABLE resultados_teste (
id              SERIAL PRIMARY KEY,
lote            VARCHAR(20)  NOT NULL,
parametro       VARCHAR(50)  NOT NULL,
valor           DECIMAL(10,2) NOT NULL,
observacao      TEXT,
criado_por      VARCHAR(50)  NOT NULL,  -- Attributable
criado_em       TIMESTAMP    DEFAULT CURRENT_TIMESTAMP, -- Contemporaneous
atualizado_por  VARCHAR(50),
atualizado_em   TIMESTAMP,
versao          INTEGER      DEFAULT 1, -- Original
ativo           BOOLEAN      DEFAULT TRUE -- Legible / Complete (soft delete)
);

-- Tabela de auditoria para todas as alterações
CREATE TABLE resultados_teste_audit (
id_audit        SERIAL PRIMARY KEY,
id_registro     INTEGER      NOT NULL,
operacao        CHAR(1)      NOT NULL, -- 'I', 'U', 'D'
usuario         VARCHAR(50)  NOT NULL,
data_operacao   TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
valor_anterior  TEXT,
valor_novo      TEXT
);

Nesse exemplo, cada princípio ALCOA++ é atendido:

  • Attributable: criado_por, atualizado_por, usuario na auditoria.
  • Legible: os dados são tipados e a auditoria armazena valores legíveis.
  • Contemporaneous: timestamps automáticos.
  • Original: versão e auditoria preservam o histórico.
  • Accurate: restrições NOT NULL, tipos adequados.
  • Complete: a auditoria registra todas as operações, inclusive DELETE.
  • Consistent: FOREIGN KEY e transações ACID.
  • Enduring: backups e retenção adequados.
  • Available: tabela de auditoria pode ser consultada por auditores.

2.2 Modelo Chave-Valor (Key-Value)

É o modelo mais simples. Cada item é armazenado como um par chave → valor, onde a chave é única e o valor pode ser qualquer dado (string, JSON, número, binário).

2.2.1 Analogia: Armário de vestiário

Pense em um armário com gavetas numeradas. A chave é o número da gaveta e o valor é o conteúdo. Para acessar, você precisa saber a chave.

SET usuario:1 "Ana Souza"
GET usuario:1

Ou com JSON:

SET sessao:abc123 '{"id":1,"carrinho":[101,102]}'

2.2.2 Casos de uso

  • Cache de sessão.
  • Carrinhos de compras.
  • Fila de mensagens.

2.2.3 Limitações

  • Consultas apenas pela chave.
  • Sem relacionamentos nativos.
  • Dificuldade para consultas complexas.

2.3 Modelo Documento

Armazena documentos estruturados (geralmente JSON ou BSON). Cada documento é uma unidade autônoma e pode conter estruturas aninhadas.

2.3.1 Analogia: Fichas de cadastro

Imagine fichas de papel de clientes, onde cada ficha pode conter campos diferentes, com subfichas para endereços ou telefones. Você guarda tudo junto, sem precisar de tabelas separadas. Como nesse exemplo prático com MongoDB.

{
"_id": 1,
"nome": "Ana Souza",
"email": "ana@email.com",
"enderecos": [
{"tipo": "casa", "cidade": "SP", "cep": "01000-000"},
{"tipo": "trabalho", "cidade": "SP", "cep": "02000-000"}
],
"pedidos": [
{"id": 101, "valor": 150.00},
{"id": 105, "valor": 230.00}
]
}

2.3.2 Casos de uso

  • Catálogos de produtos.
  • Blogs e sistemas de conteúdo.
  • Aplicações que exigem evolução rápida do esquema.

2.3.3 Vantagens e desvantagens

  • Vantagem: flexibilidade de esquema, leitura rápida de dados agregados.
  • Desvantagem: redundância e risco de inconsistência.

2.4 Modelo Colunar (Column-Family)

Os dados são organizados por famílias de colunas, e não por linhas. É otimizado para leitura de muitas colunas de poucas linhas ao mesmo tempo.

2.4.1 Analogia: Planilha invertida

Imagine uma planilha onde cada coluna é armazenada separadamente. Para somar todos os valores de uma coluna, você lê apenas essa coluna, não a planilha inteira. Como nesse exemplo usando Cassandra.

CREATE TABLE vendas (
produto_id UUID,
data timestamp,
quantidade int,
valor decimal,
PRIMARY KEY (produto_id, data)
);

Os dados de quantidade e valor são armazenados em estruturas separadas por coluna, otimizando agregações.

2.4.2 Casos de uso

  • Séries temporais (sensores, logs).
  • Análise de grandes volumes de dados (OLAP).
  • Sistemas de recomendação.

2.4.3 Vantagens e desvantagens

  • Vantagem: compressão e leitura rápida de colunas específicas.
  • Desvantagem: complexidade de modelagem e consultas limitadas.

2.5 Modelo Grafo

Os dados são representados como nós (entidades) e arestas (relacionamentos). Cada nó e aresta pode ter propriedades.

2.5.1 Analogia: Mapa de amizades

Imagine um mapa de amigos em uma rede social. Cada pessoa é um nó, e a amizade é uma aresta. Você pode navegar de pessoa para pessoa seguindo as arestas. Como nesse exemplo usando Neo4j.

CREATE (ana:Cliente {nome: "Ana"})
CREATE (bruno:Cliente {nome: "Bruno"})
CREATE (ana)-[:COMPROU]->(produto:Produto {nome: "Notebook"})
CREATE (bruno)-[:COMPROU]->(produto)

Consulta de recomendação:

MATCH (a:Cliente)-[:COMPROU]->(p:Produto)<-[:COMPROU]-(b:Cliente)
WHERE a.nome = "Ana"
RETURN b.nome, p.nome

2.5.2 Casos de uso

  • Redes sociais.
  • Detecção de fraudes.
  • Sistemas de recomendação.
  • Rotas e logística.

2.5.3 Vantagens e desvantagens

  • Vantagem: consultas de relacionamentos complexos de forma eficiente e intuitiva.
  • Desvantagem: menos maduro para transações financeiras; escala vertical limitada.

3. Introdução: evolução, arquitetura e propriedades dos SGBDs

3.1 Do sistema de arquivos ao SGBD

Antes da adoção ampla dos Sistemas Gerenciadores de Banco de Dados, muitas aplicações armazenavam informações em arquivos próprios. Esse modelo, conhecido como Sistema Gerenciador de Arquivos (SGA), fazia com que cada programa controlasse diretamente seus arquivos e formatos. Com o crescimento dos sistemas, essa organização passou a gerar problemas de redundância, inconsistência, dificuldade de consulta, dependência entre programas e dados, segurança e recuperação de falhas.

Aspecto SGA (arquivos tradicionais) SGBD
ArmazenamentoArquivos separados, controlados pelas aplicaçõesBase centralizada ou distribuída, gerenciada por um software específico
RedundânciaÉ comum manter cópias do mesmo dado em arquivos diferentesPermite controlar a redundância e compartilhar os dados
IndependênciaAlterações no formato podem exigir mudanças nos programasOferece independência física e lógica, dentro dos limites do esquema
IntegridadeRegras ficam espalhadas pelo código das aplicaçõesRestrições podem ser centralizadas no banco
ConcorrênciaDifícil coordenar acessos simultâneosPossui mecanismos de transação e controle de concorrência
SegurançaFrequentemente depende de controles implementados em cada aplicaçãoPermissões, autenticação, papéis e auditoria centralizados
RecuperaçãoDepende de rotinas específicas de cada programaOferece logs, backup e mecanismos de recuperação

Independência física: permite alterar a organização física dos dados — por exemplo, índices, arquivos, discos ou localização do armazenamento — sem exigir alterações nas aplicações que utilizam o esquema lógico.

Independência lógica: permite modificar aspectos do esquema lógico, como acrescentar atributos ou criar novas relações, preservando as aplicações que não dependem dessas mudanças. Na prática, a independência depende de como as aplicações acessam os dados e das alterações realizadas.

3.2 Arquitetura em camadas

O SGBD atua como intermediário entre as aplicações e o armazenamento. A aplicação envia comandos por meio de uma linguagem ou API; o SGBD interpreta e otimiza as solicitações, verifica permissões e integridade, coordena transações e solicita ao sistema operacional as operações de leitura e gravação.

CamadaExemplosResponsabilidade
AplicaçãoPHP, JavaScript, C#Implementa as regras e a interface do sistema; solicita operações sobre os dados.
SGBDMySQL, Oracle, SQL Server, MongoDBGerencia estruturas, consultas, transações, segurança e integridade.
Sistema operacionalWindows, Linux, macOS, AndroidGerencia processos, memória, arquivos e dispositivos.
ArmazenamentoHD, SSD e outros meiosPersiste fisicamente os dados.

Essa separação reduz o acoplamento: a aplicação não precisa conhecer setores do disco nem a forma interna como o SGBD organiza os registros.

3.3 Tipos de arquitetura de SGBD

TipoOrganizaçãoCaracterística principal
CentralizadaBanco e processamento concentrados em uma máquinaAdministração mais simples, mas maior dependência do servidor central.
ParalelaUma base processada por vários processadores e/ou discos em paraleloBusca acelerar consultas e aumentar a capacidade de processamento.
DistribuídaPartes ou réplicas dos dados ficam em diferentes nós conectados por redePermite distribuição geográfica, escalabilidade e disponibilidade, exigindo coordenação entre nós.

Arquitetura paralela e distribuída não são sinônimos: a paralela enfatiza a execução simultânea em recursos de processamento; a distribuída envolve nós autônomos que se comunicam por uma rede.

3.4 Propriedades ACID

Uma transação é uma unidade lógica de trabalho formada por operações que devem ser tratadas em conjunto. As propriedades ACID ajudam a garantir confiabilidade em operações como transferências bancárias, pagamentos e matrículas.

PropriedadeSignificadoExemplo
AtomicidadeTodas as operações da transação são confirmadas ou nenhuma delas permanece aplicada.Uma transferência não pode debitar uma conta e deixar de creditar a outra.
ConsistênciaA transação deve preservar as regras e restrições de integridade do banco.Uma conta não pode violar uma regra de saldo mínimo definida pelo sistema.
IsolamentoTransações concorrentes não devem produzir interferências indevidas; o nível de isolamento define o que uma transação pode observar.Uma operação não deve utilizar um valor intermediário que outra transação ainda pode desfazer.
DurabilidadeApós o COMMIT, as alterações confirmadas devem sobreviver a falhas previstas pelo mecanismo de recuperação.Uma transferência confirmada não deve desaparecer após uma queda de energia.

3.5 Modelo Entidade-Relacionamento (E-R)

O modelo Entidade-Relacionamento representa conceitualmente um recorte do mundo real. É utilizado para compreender os requisitos antes de decidir como as informações serão implementadas em tabelas.

  • Entidade: objeto ou conceito sobre o qual se deseja armazenar informações, como Cliente, Produto, Médico ou Consulta.
  • Atributo: característica de uma entidade ou relacionamento, como nome, data de nascimento ou preço.
  • Relacionamento: associação entre entidades, como Cliente realiza Venda ou Médico atende Paciente.
  • Cardinalidade: indica quantas ocorrências de uma entidade podem se associar às ocorrências de outra.

3.5.1 Cardinalidades

CardinalidadeExemploInterpretação
1:1Pessoa — EstudanteUma pessoa pode corresponder a, no máximo, um registro de estudante, e vice-versa, conforme a regra do domínio.
1:NCliente — VendaUm cliente pode realizar várias vendas; cada venda pertence a um cliente.

Para descobrir a cardinalidade, faça a pergunta nos dois sentidos: “uma ocorrência de A pode estar relacionada a quantas ocorrências de B?” e “uma ocorrência de B pode estar relacionada a quantas ocorrências de A?”. Considere também a participação mínima: zero (opcional) ou um (obrigatória).

3.5.2 Tipos de atributos

  • Monovalorado: possui um único valor por ocorrência, como data de nascimento.
  • Multivalorado: pode possuir vários valores, como telefones de uma pessoa.
  • Composto: pode ser decomposto em partes, como endereço (rua, número, cidade e CEP).

Na transformação para o modelo relacional, atributos multivalorados normalmente são representados em uma tabela própria; atributos compostos podem ser decompostos em colunas atômicas; relacionamentos N:N são implementados por uma tabela associativa.

3.6 Modelo relacional: tabelas, chaves e integridade

No modelo relacional, os dados são organizados em relações, normalmente implementadas como tabelas. As colunas representam atributos e as linhas representam tuplas (registros).

  • Chave primária (PK): atributo ou conjunto de atributos que identifica unicamente cada linha. Não deve aceitar valores duplicados nem nulos.
  • Chave estrangeira (FK): atributo ou conjunto de atributos que referencia uma chave candidata/primária de outra tabela (ou da própria tabela).
  • Chave composta: chave formada por mais de um atributo, comum em tabelas associativas.
  • Entidade forte: possui identificação própria e pode existir independentemente de outra entidade.
  • Entidade fraca: depende de outra entidade para sua identificação ou existência, conforme as regras do modelo.

Integridade de entidade: a chave primária identifica unicamente cada registro. Integridade referencial: uma FK deve apontar para um registro existente na tabela referenciada, ou aceitar NULL quando a regra e a definição permitirem. Integridade de domínio: os valores devem respeitar o tipo, formato e restrições estabelecidos para o atributo.

Ao excluir ou atualizar um registro referenciado, o SGBD pode restringir a operação ou aplicar ações em cascata, conforme as regras configuradas (por exemplo, RESTRICT/NO ACTION, CASCADE ou SET NULL). A escolha deve refletir as regras do negócio.

4. SQL: linguagem e grupos de comandos

SQL significa Structured Query Language (Linguagem de Consulta Estruturada). É a linguagem mais utilizada para definir estruturas, manipular registros, controlar permissões e consultar bancos relacionais. O padrão SQL foi publicado pela ANSI em 1986 e evoluiu ao longo de diferentes versões.

DDL cria, modifica e elimina objetos como bancos de dados e tabelas. Exemplo de criação de tabelas com chave primária e estrangeira:

CREATE TABLE aluno (

);

);
CREATE TABLE matricula (

-- Adicionar uma coluna

A sintaxe de ALTER TABLE pode variar entre SGBDs. Antes de executar DROP ou alterações destrutivas, confirme dependências e faça backup quando necessário.

4.3 DML — manipulação de registros

-- Inserir registros
INSERT INTO aluno (codigo, nome, idade)
VALUES (1, 'João da Silva', 18);

-- Atualizar registros: use WHERE para limitar as linhas afetadas
UPDATE aluno
SET idade = 19
WHERE codigo = 1;

-- Excluir registros: sem WHERE, todas as linhas podem ser removidas
DELETE FROM aluno
WHERE codigo = 1;

Atenção: UPDATE e DELETE sem WHERE podem alterar ou excluir todos os registros da tabela. Em atividades práticas, confira a condição e, quando possível, execute antes um SELECT com o mesmo filtro.

4.4 DCL — controle de acesso

-- Criar usuário (exemplo MySQL)
CREATE USER 'jose'@'localhost' IDENTIFIED BY 'senha_forte';

-- Conceder permissões
GRANT SELECT, INSERT, UPDATE, DELETE
ON escola.* TO 'jose'@'localhost';

-- Revogar uma permissão específica
REVOKE DELETE
ON escola.aluno FROM 'jose'@'localhost';

O princípio do menor privilégio recomenda conceder apenas as permissões necessárias para cada usuário. CREATE USER e a forma de identificar host/usuário podem variar conforme o SGBD.

4.5 DTL/TCL — controle de transações

START TRANSACTION;
UPDATE conta
SET saldo = saldo - 100
WHERE codigo = 1;
UPDATE conta
SET saldo = saldo + 100
WHERE codigo = 2;

-- Confirma todas as operações da transação
COMMIT;

-- Em caso de erro, desfaz as operações ainda não confirmadas:
-- ROLLBACK;

COMMIT confirma as alterações da transação. ROLLBACK desfaz as alterações ainda não confirmadas. O comportamento de autocommit e as operações que podem participar de transações dependem do SGBD e do mecanismo de armazenamento utilizado.

4.6 Concorrência e recuperação de falhas

Concorrência ocorre quando duas ou mais transações são executadas em períodos sobrepostos. Sem controle adequado, podem surgir anomalias:

  • Atualização perdida: duas transações leem o mesmo valor; uma grava sua alteração e, depois, a outra grava um valor calculado a partir do estado antigo, sobrescrevendo a primeira atualização.
  • Atualização temporária (leitura suja): uma transação lê uma alteração ainda não confirmada por outra; se a primeira transação sofrer ROLLBACK, a segunda terá utilizado um dado que não deveria ser considerado definitivo.
  • Deadlock: transações ficam aguardando recursos bloqueados umas pelas outras, formando um ciclo de espera. O SGBD normalmente detecta a situação e aborta uma das transações.

Os SGBDs utilizam mecanismos como bloqueios, controle de versões (MVCC), níveis de isolamento e logs para coordenar acessos. A recuperação também considera falhas de hardware, software, rede, energia e erros de execução. Backups e logs de transação ajudam a restaurar o banco a um estado consistente.

4.7 Exemplos práticos das anomalias de concorrência

Os três problemas clássicos de concorrência descritos na seção anterior podem ser visualizados com execuções entrelaçadas de duas transações. Abaixo, cada anomalia é apresentada com um cenário concreto e a sequência de operações que a produz.

4.7.1 Atualização perdida (Lost Update)

Cenário: dois caixas eletrônicos sacam da mesma conta ao mesmo tempo. O saldo inicial é R$ 1.000,00 e cada saque é de R$ 100,00. O resultado correto deveria ser R$ 800,00; a anomalia produz R$ 900,00.

TempoTransação T1 (Caixa A)Transação T2 (Caixa B)Saldo no banco
t1Lê saldo = 1000—1000
t2—Lê saldo = 10001000
t3saldo = 1000 − 100 = 900—1000
t4—saldo = 1000 − 100 = 9001000
t5Grava saldo = 900—900
t6COMMIT—900
t7—Grava saldo = 900900
t8—COMMIT900 (errado!)

O que aconteceu: T2 leu o saldo antigo (1000) antes de T1 gravar sua alteração. Ao gravar 900 em t7, T2 sobrescreveu o valor calculado por T1 em t5. O saque de T1 foi perdido: o saldo final deveria ser 800 (dois saques de 100), mas ficou 900.

Como evitar: bloqueio exclusivo na leitura para atualização (SELECT ... FOR UPDATE), controle de versões (MVCC) com verificação de versão no UPDATE, ou nível de isolamento REPEATABLE READ/SERIALIZABLE.

4.7.2 Atualização temporária / leitura suja (Dirty Read)

Cenário: T1 transfere R$ 500,00 para a conta de T2 e, antes de confirmar, T2 consulta o saldo e decide fazer uma compra. T1 sofre ROLLBACK e o dinheiro nunca existiu.

TempoTransação T1 (Transferência)Transação T2 (Consulta/Compra)Saldo da conta de T2
t1Debita R$ 500 da conta de origem—1000
t2Credita R$ 500 na conta de T2 (não confirmado)—1500 (não confirmado)
t3—Lê saldo = 15001500 (não confirmado)
t4—Autoriza compra de R$ 1.2001500 (não confirmado)
t5ROLLBACK (falha na transferência)—1000 (valor real)
t6—Compra já autorizada com base em 15001000 (insuficiente!)

O que aconteceu: T2 leu um valor que T1 ainda não havia confirmado. Quando T1 sofreu ROLLBACK, o saldo voltou a 1000, mas T2 já havia tomado uma decisão (compra de R$ 1.200) baseada em um dado que nunca existiu oficialmente. Isso é a leitura suja: T2 "sujou-se" com um dado temporário.

Como evitar: nível de isolamento mínimo READ COMMITTED (impede leitura de dados não confirmados); bloqueios de leitura compartilhada; MVCC com visibilidade apenas de versões confirmadas.

4.7.3 Deadlock (impasse)

Cenário: duas transações precisam atualizar as mesmas duas contas, mas em ordens opostas. T1 bloqueia a Conta A e precisa da Conta B; T2 bloqueia a Conta B e precisa da Conta A. Nenhuma consegue prosseguir.

TempoTransação T1Transação T2Situação dos bloqueios
t1UPDATE conta SET saldo = saldo - 100 WHERE id = 'A'—A bloqueada por T1
t2—UPDATE conta SET saldo = saldo - 200 WHERE id = 'B'B bloqueada por T2
t3UPDATE conta SET saldo = saldo + 100 WHERE id = 'B' → espera—T1 aguarda B (detida por T2)
t4—UPDATE conta SET saldo = saldo + 200 WHERE id = 'A' → esperaT2 aguarda A (detida por T1) → ciclo de espera
 
T1 detém A, espera B
        T2 detém B, espera A
                ↺ ciclo de espera (deadlock)

O que aconteceu: formou-se um ciclo de espera. Nenhuma transação pode avançar porque cada uma detém o recurso que a outra precisa. O SGBD detecta o ciclo (por grafo de espera ou timeout) e aborta uma das transações (por exemplo, T2), liberando seus bloqueios. T1 prossegue; T2 precisa ser reexecutada pela aplicação.

Como evitar: definir uma ordem global de aquisição de recursos (ex.: sempre atualizar contas em ordem crescente de id); manter transações curtas; usar SELECT ... FOR UPDATE com ordem consistente; configurar innodb_lock_wait_timeout (MySQL) ou deadlock_timeout (PostgreSQL) para detecção por timeout; tratar o erro de deadlock na aplicação com retry.

5. DQL: consultas com SELECT

5.1 Estrutura geral

SELECT coluna1, coluna2
FROM tabela1
INNER JOIN tabela2 ON tabela1.chave = tabela2.chave
WHERE condicao
GROUP BY coluna1, coluna2
HAVING condicao_de_grupo
ORDER BY coluna1 ASC;

Em termos conceituais, a consulta pode envolver junção de tabelas, filtragem de linhas, agrupamento, filtragem dos grupos, projeção das colunas e ordenação do resultado. A ordem escrita das cláusulas não é necessariamente a ordem física escolhida pelo otimizador.

5.3 Junções (JOIN)

-- INNER JOIN: retorna apenas correspondências entre as tabelas
SELECT a.nome, c.nome AS curso
FROM aluno a
INNER JOIN matricula m ON m.codigo_alu = a.codigo
INNER JOIN curso c ON c.codigo = m.codigo_cur;

-- LEFT JOIN: mantém todas as linhas da tabela à esquerda
SELECT a.nome, m.codigo_cur
FROM aluno a
LEFT JOIN matricula m ON m.codigo_alu = a.codigo;

Use aliases para abreviar nomes de tabelas. A condição ON explicita como as linhas se relacionam. Um JOIN sem condição adequada pode produzir produto cartesiano e multiplicar linhas inesperadamente.

6.2 Plano de execução

Como roteiro didático para construir a árvore de operações, os slides adotam: junção, seleção, agrupamento, seleção de grupos, projeção e ordenação. Essa sequência é uma convenção de representação para os exercícios; o otimizador real pode reordenar operações equivalentes para reduzir custo, desde que preserve o resultado.

  • Junção: conecta as relações necessárias.
  • Seleção: reduz as linhas por condição.
  • Agrupamento: reúne linhas por atributos e calcula funções.
  • Seleção de grupo: aplica HAVING.
  • Projeção: mantém as colunas solicitadas.
  • Ordenação: aplica a ordem final.

7. Normalização de dados

Normalização é um processo sistemático de organização das tabelas para reduzir redundância e evitar anomalias de inserção, atualização e exclusão. O processo analisa dependências entre atributos e separa informações que representam fatos diferentes.

7.1 Anomalias que a normalização procura evitar

  • Anomalia de inserção: não é possível cadastrar um fato sem cadastrar outro fato não relacionado.
  • Anomalia de atualização: o mesmo dado aparece repetido em várias linhas e precisa ser alterado em todos os lugares.
  • Anomalia de exclusão: ao apagar uma linha, perde-se também uma informação que deveria continuar armazenada.

7.2 Primeira Forma Normal (1FN)

Uma relação está na 1FN quando cada atributo contém valores atômicos no contexto do domínio e não existem grupos repetidos ou listas de valores em uma única célula. Telefones, produtos ou itens de uma nota fiscal não devem ser armazenados como uma lista em uma coluna da tabela principal.

Exemplo: separar o cabeçalho da nota fiscal dos itens que ela contém.

NOTA_FISCAL(nr_nf PK, data_emissao, codigo_cliente FK, valor_total)

ITEM_NOTA(
nr_nf PK/FK, codigo_produto PK/FK,
quantidade, valor_unitario
)

7.3 Segunda Forma Normal (2FN)

Uma relação está na 2FN quando está na 1FN e cada atributo não-chave depende da chave primária inteira, não apenas de parte dela. A dependência parcial é relevante quando a chave primária é composta por dois ou mais atributos.

Se (nr_nf, codigo_produto) identifica um item da nota, atributos como descrição do produto e unidade dependem apenas de codigo_produto, não da chave composta inteira. Esses atributos devem ficar na tabela PRODUTO.

ITEM_NOTA(nr_nf PK/FK, codigo_produto PK/FK, quantidade, valor_unitario)

PRODUTO(codigo_produto PK, nome_produto,unidade, tributacao)

7.4 Terceira Forma Normal (3FN)

Uma relação está na 3FN quando está na 2FN e não possui dependências transitivas de atributos não-chave em relação à chave. Em termos práticos, um atributo não-chave não deve depender de outro atributo não-chave.

Se a tabela NOTA_FISCAL contém codigo_cliente e nome_cliente, endereço e cidade do cliente, esses dados dependem do código do cliente, e não diretamente do número da nota. Devem ser armazenados na tabela CLIENTE.

NOTA_FISCAL(nr_nf PK, data_emissao, codigo_cliente FK, valor_total)
CLIENTE(codigo_cliente PK, nome, rua, cidade, uf)

7.5 Quarta Forma Normal (4FN)

A 4FN trata dependências multivaloradas independentes. Quando uma entidade possui vários valores de um atributo que não dependem uns dos outros — por exemplo, vários telefones —, esses valores devem ser representados em uma relação separada.

CLIENTE(codigo_cliente PK, nome, endereco)
TELEFONE_CLIENTE(
codigo_cliente PK/FK,
telefone PK
)

O objetivo não é criar tabelas em excesso, mas representar cada fato no lugar adequado, com chaves e relacionamentos coerentes. A normalização deve considerar as regras reais do negócio.

10.1 Introdução

1) Uma organização de grande porte decidiu atualizar sua infraestrutura de TI, migrando o armazenamento de seus dados de arquivos planos em discos rígidos locais (HDDs) para uma estrutura distribuída em nuvem com novos métodos de indexação e compressão. No paradigma antigo do Sistema Gerenciador de Arquivos (SGA), essa alteração na camada física exigiria a reescrita e a recompilação dos códigos-fonte de todas as aplicações que acessavam os dados. Com a adoção de um Sistema Gerenciador de Banco de Dados (SGBD), essa mudança pôde ser realizada na camada de armazenamento sem causar qualquer impacto ou necessidade de alteração nas aplicações existentes.

Qual recurso técnico do SGBD assegura a neutralidade das aplicações diante de mudanças na estrutura de armazenamento no disco?

A) Independência de dados

B) Dependência de dados

C) Gerenciamento de transações

D) Integridade nos dados

E) Facilidade no acesso aos dados

Resolução: A) Independência de dados. A independência física de dados permite alterar a organização física (índices, arquivos, discos, compressão) sem reescrever as aplicações que usam o esquema lógico. É um dos principais benefícios do SGBD em relação ao SGA.

2) No desenvolvimento de sistemas corporativos, a arquitetura de software e banco de dados é organizada em camadas com responsabilidades bem definidas. Em um sistema web construído em linguagens como C#, JavaScript ou PHP, a aplicação não manipula diretamente os blocos e setores de um disco rígido (HD ou SSD). Em vez disso, a camada de aplicação comunica-se com o Sistema Gerenciador de Banco de Dados (SGBD) — como MySQL, Oracle ou MongoDB —, que por sua vez se apoia no Sistema Operacional para realizar a persistência física.

Considerando a arquitetura representada pela cadeia Aplicação -> SGBD -> Armazenamento, qual é o papel fundamental desempenhado pela camada intermediária (SGBD) nessa organização?

A) Executar diretamente o código das linguagens de programação de aplicação (como PHP ou C#), substituindo a necessidade de servidores web e interpretadores.

B) Atuar como camada de abstração e gerenciamento, isolando o código de aplicação dos detalhes de baixo nível do sistema operacional e dos dispositivos físicos de armazenamento.

C) Traduzir instruções de software em sinais elétricos diretos para o firmware do SSD/HD, eliminando a dependência do Sistema Operacional.

D) Unificar a aplicação e o armazenamento físico em um único bloco monolítico, tornando obrigatória a reescrita do sistema caso o banco de dados seja trocado.

E) Limitar as conexões de software apenas a modelos relacionais tradicionais (como MySQL e Oracle), inviabilizando a integração com tecnologias não relacionais (como MongoDB).

Resolução: B) O SGBD atua como camada de abstração e gerenciamento, isolando a aplicação dos detalhes de baixo nível (sistema operacional e dispositivos físicos). Ele interpreta comandos, otimiza consultas, verifica permissões e integridade, coordena transações e solicita ao SO as operações de leitura/gravação.

3) Ao planejar a infraestrutura de TI de um banco de dados, a equipe de arquitetura deve definir o tipo de SGBD a adotar quanto ao arranjo de processamento e armazenamento físico. As três abordagens clássicas de arquitetura são:

a) Centralizada: O SGBD e os dados residem em uma única máquina.

b) Paralela: Múltiplos processadores/discos trabalham de forma simultânea e fortemente acoplada para aumentar a velocidade de processamento de consultas.

c) Distribuída: O banco de dados é dividido em múltiplos nós autônomos e geograficamente/fisicamente separados, conectados via rede de comunicação.

Considerando a diferenciação técnica entre essas três arquiteturas de SGBD, assinale a alternativa correta:

A) O SGBD distribuído caracteriza-se pelo acoplamento forte de hardware, onde múltiplos processadores obrigatoriamente compartilham o mesmo barramento e a mesma memória RAM física no mesmo gabinete.

B) O SGBD centralizado oferece alta disponibilidade nativa contra falhas de hardware, pois replica automaticamente as transações em múltiplos servidores distribuídos na rede.

C) O SGBD paralelo tem como objetivo principal utilizar a concorrência de múltiplos processadores/discos (em um ambiente de computação de alto desempenho) para acelerar a execução de consultas e o volume de transações por segundo.

D) O SGBD distribuído elimina a necessidade de transparência de localização, exigindo que o usuário final conheça o endereço IP exato do nó onde o dado solicitado está fisicamente armazenado.

E) O SGBD paralelo diferencia-se do distribuído por depender de uma rede de longa distância (WAN) para conectar nós de processamento autônomos localizados em diferentes cidades.

Resolução: C) O SGBD paralelo usa múltiplos processadores/discos em paralelo (acoplamento forte) para acelerar consultas e aumentar o throughput de transações. A alternativa A confunde paralelo com distribuído; B descreve falsamente a centralizada; D contradiz a transparência de localização; E inverte as características.

4) Após a definição dos tipos de SGBD em relação à infraestrutura física e de processamento, a arquitetura de um sistema exige a escolha do modelo de dados. O modelo de dados é a abstração que fornece o conjunto de ferramentas conceituais, estruturais e notações para descrever como as informações são organizadas, como os elementos se relacionam entre si, qual é a semântica dos dados e quais restrições de integridade devem ser impostas. Ao longo da evolução da tecnologia de bancos de dados, diversos modelos foram propostos e adotados (tais como os modelos Hierárquico, em Rede, Relacional, Entidade-Relacionamento, Orientado a Objetos e NoSQL).

Considerando a definição e a finalidade dos modelos de dados, assinale a alternativa correta:

A) O modelo de dados restringe-se à especificação dos componentes físicos de hardware (como arranjos de discos SSD e controladores de memória), não interferindo na forma lógica como os desenvolvedores visualizam os dados.

B) A adoção de um modelo de dados é um procedimento exclusivo de bancos de dados relacionais executados em arquitetura centralizada, sendo dispensável em SGBDs modernos.

C) O modelo de dados define unicamente os comandos de consulta em linguagem SQL, não abrangendo os níveis de modelagem conceitual ou lógica do sistema.

D) O modelo de dados atua como uma linguagem/framework de abstração que define as regras estruturais, os padrões de organização e as restrições lógicas aplicadas aos dados mantidos pelo SGBD.

E) Os modelos de dados eliminam a necessidade de definir tipos de dados para os atributos, permitindo que a aplicação grave informações no SGBD sem qualquer esquema conceitual.

Resolução: D) O modelo de dados é uma abstração que define estruturas, relacionamentos, semântica e restrições de integridade — servindo de base para a modelagem conceitual, lógica e física, independentemente do SGBD ou arquitetura.

5) Em um Sistema Gerenciador de Banco de Dados (SGBD) transacional, a execução de um conjunto de operações de leitura e escrita deve ser tratada como uma unidade lógica de trabalho. Para garantir a confiabilidade e o processamento correto dos dados, o SGBD implementa as quatro propriedades conhecidas pelo acrônimo ACID.

Cenário 1: Uma transação de transferência bancária completa com sucesso e recebe a confirmação (commit). Segundos depois, ocorre uma queda abrupta de energia elétrica no datacenter. Ao religar o servidor, o SGBD garante que os saldos atualizados continuam gravados no banco de dados e não foram perdidos.

Cenário 2: Durante a execução de uma transferência de fundos, o valor é debitado da Conta A, mas o sistema falha antes de creditar a Conta B. O SGBD interfere e desfaz o débito parcial, assegurando que o sistema retorne ao estado original e a operação não fique gravada pela metade.

Os comportamentos descritos no Cenário 1 e no Cenário 2 exemplificam, respectivamente, quais propriedades ACID?

A) Atomicidade e Isolamento.

B) Consistência e Durabilidade.

C) Isolamento e Consistência.

D) Atomicidade e Durabilidade.

E) Durabilidade e Atomicidade.

Resolução: E) Durabilidade e Atomicidade. Cenário 1 → após o COMMIT, as alterações sobrevivem à falha (durabilidade). Cenário 2 → o débito parcial é desfeito, garantindo que a transação seja tudo ou nada (atomicidade).

12) A concorrência ocorre quando múltiplas transações são executadas simultaneamente em um SGBD. Quando duas ou mais transações tentam acessar ou modificar o mesmo dado ao mesmo tempo, a falta de controle de concorrência pode levar a inconsistências. Considere as duas situações de execução entrelaçada entre duas transações bancárias, T1 (Transferência) e T2 (Depósito):

Situação I: T1 lê o valor da ContaX. Logo em seguida, antes que T1 termine, T2 também lê o valor inicial da ContaX. T1 realiza o débito e atualiza o saldo. Na sequência, T2 efetua o crédito e grava o novo saldo na ContaX, sobrescrevendo a alteração de T1 e fazendo com que o débito de T1 seja ignorado.

Situação II: T1 altera o valor da ContaX. Em seguida, T2 lê esse novo saldo atualizado por T1 e o utiliza em seus cálculos. Contudo, antes de finalizar, T1 sofre uma falha e sua atualização é desfeita (rollback). Como resultado, T2 realizou suas operações baseando-se em um valor que nunca foi confirmado definitivamente.

As anomalias descritas na Situação I e na Situação II correspondem, respectivamente, a quais problemas clássicos de concorrência?

A) Problema da Atualização Temporária e Problema da Atualização Perdida.

B) Problema do Deadlock e Problema da Atualização Perdida.

C) Problema da Atualização Perdida e Problema da Atualização Temporária.

D) Problema da Inconsistência de Dados e Problema da Falha de Hardware.

E) Problema da Atualização Perdida e Problema de Integridade Física.

Resolução: C) Problema da Atualização Perdida e Problema da Atualização Temporária. Situação I → T2 sobrescreve a alteração de T1 (atualização perdida). Situação II → T2 lê valor não confirmado que sofre rollback (atualização temporária / leitura suja).

10.7 Normalização

19) Para cada uma das modelagens a seguir, aplique as formas normais necessárias.

Lembrete das formas normais:

  • 1FN: todos os atributos atômicos; sem grupos repetidos ou listas em uma célula.
  • 2FN: na 1FN e todo atributo não-chave depende da chave primária inteira (sem dependência parcial).
  • 3FN: na 2FN e sem dependência transitiva (atributo não-chave que depende de outro atributo não-chave).
  • 4FN: na 3FN e sem dependência multivalorada independente (dois ou mais atributos multivalorados que não se relacionam entre si).
a) Curso / Aluno / Disciplina

Relação original:

Curso (codigo_curso PK, nome_curso, codigo_aluno, nome_aluno,
       telefone_aluno, codigo_disciplina, nome_disciplina)

Passo 1 — 1FN (eliminar grupos repetidos): um curso tem vários alunos e várias disciplinas; um aluno tem vários telefones. Tudo está "espremido" em uma única linha → grupos repetidos e atributo multivalorado (telefone_aluno).

Ação:

CURSO (codigo_curso PK, nome_curso)
ALUNO (codigo_aluno PK, nome_aluno)
TELEFONE_ALUNO (codigo_aluno PK/FK, telefone PK)
DISCIPLINA (codigo_disciplina PK, nome_disciplina)
CURSO_ALUNO (codigo_curso PK/FK, codigo_aluno PK/FK)
CURSO_DISCIPLINA (codigo_curso PK/FK, codigo_disciplina PK/FK)

Resultado: todas as relações têm atributos atômicos → 1FN atingida.

Passo 2 — 2FN (eliminar dependências parciais): nas relações com chave composta (CURSO_ALUNO, CURSO_DISCIPLINA) não há atributos não-chave — logo, não há dependência parcial. Nas demais, a chave é simples. → 2FN atingida.

Passo 3 — 3FN (eliminar dependências transitivas): nome_aluno depende de codigo_aluno (PK); nome_disciplina depende de codigo_disciplina; nome_curso depende de codigo_curso. Nenhuma dependência transitiva. → 3FN atingida.

Passo 4 — 4FN (eliminar dependências multivaloradas independentes): o telefone multivalorado já foi isolado em TELEFONE_ALUNO; os multivalorados "alunos do curso" e "disciplinas do curso" estão em relações separadas, sem dependência entre si. → 4FN atingida.

Modelo final:

CURSO (codigo_curso PK, nome_curso)
ALUNO (codigo_aluno PK, nome_aluno)
TELEFONE_ALUNO (codigo_aluno PK/FK, telefone PK)
DISCIPLINA (codigo_disciplina PK, nome_disciplina)
CURSO_ALUNO (codigo_curso PK/FK, codigo_aluno PK/FK)
CURSO_DISCIPLINA (codigo_curso PK/FK, codigo_disciplina PK/FK)
b) Quarto / Paciente / Médico

Relação original:

Quarto (num_quarto PK, descricao_quarto, num_paciente, nome_paciente,
        cod_medico, nome_medico, fones_medico)

Passo 1 — 1FN: um quarto pode ter vários pacientes e vários médicos; um médico pode ter vários telefones. Tudo em uma linha → grupos repetidos e atributo multivalorado (fones_medico).

QUARTO (num_quarto PK, descricao_quarto)
